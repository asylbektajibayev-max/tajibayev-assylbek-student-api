## Linux

- Linux — семейство ОС на базе ядра Linux. В DevOps используется благодаря автоматизации, серверной экосистеме, контейнерам и доступным инструментам.
- `pwd` выводит абсолютный путь текущего каталога.
- Абсолютный путь начинается от `/`; относительный вычисляется от текущего каталога.
- `mkdir dir` создаёт каталог; `mkdir -p a/b` создаёт и недостающие родительские каталоги.
- `touch file` создаёт пустой файл, если его нет; если он есть, обновляет время.
- `ls -la` показывает скрытые файлы и подробные права.
- `cp` копирует; `mv` перемещает или переименовывает.
- Shebang `#!/bin/bash` указывает интерпретатор при прямом запуске исполняемого скрипта.
- Сделать скрипт исполняемым: `chmod u+x script.sh`. В этой работе `chmod 744` задаёт владельцу rwx, группе r--, остальным r--.
- `755` означает rwxr-xr-x: владелец может читать, писать и исполнять; группа и остальные — читать и исполнять.
- `chmod` меняет права доступа к файлам и каталогам.
- Аргументы Bash: `$1`, `$2`; `"$@"` — все аргументы с сохранением границ; `$#` — число аргументов.
- `>` перезаписывает вывод в файл; `>>` дописывает. Оба создают файл, если его нет.
- `df -h` показывает ёмкость, занятое и доступное место файловых систем; `du -sh dir` — размер каталога.
- `free -h` показывает память и swap; available полезнее free для оценки доступной приложениям памяти из-за кэша ОС.
- Процесс — выполняющаяся программа со своим PID и ресурсами. Список: `ps aux`, динамически: `top`.
- Найти процесс: `pgrep -af java`. Завершить: `kill PID` посылает SIGTERM; `kill -9 PID` — крайний вариант без штатного завершения.
- Последние пять строк: `tail -n 5 file.log`.
- Поиск: `grep -F 'Tajibayev' file.log`. Сохранить: `grep -F 'Tajibayev' file.log > Tajibayev_Assylbek_log_analysis.txt`.

## Git и GitHub

- Git — распределённая система контроля версий; GitHub — сервис размещения Git-репозиториев и совместной работы.
- `git init` создаёт локальный репозиторий.
- Рабочий каталог содержит изменяемые файлы; staging area — выбранные изменения для следующего коммита; repository — история коммитов и объектов.
- `git status` показывает текущую ветку, staged/unstaged/untracked файлы и состояние синхронизации с upstream, если он задан.
- `git add` добавляет текущее содержимое выбранных файлов в staging area.
- `git commit` сохраняет снимок staged-изменений с автором, сообщением и ссылками на родителей. Сам по себе не отправляет данные на GitHub.
- Осмысленные сообщения объясняют цель изменения, облегчают ревью, поиск регрессий и восстановление истории.
- Ветка — перемещаемая ссылка на коммит. Она позволяет независимо разрабатывать функции. Создать и переключиться: `git switch -c feature/name`.
- Merge объединяет историю веток и при необходимости создаёт merge commit. Rebase переносит коммиты поверх другого основания и меняет их идентификаторы; опубликованную общую историю без согласования не переписывают.
- Конфликт возникает, когда Git не может автоматически согласовать изменения, например разные правки одной строки.
- Разрешение README: открыть файл, выбрать итоговый текст, удалить маркеры `<<<<<<<`, `=======`, `>>>>>>>`, выполнить `git add README.md`, затем `git commit`. Важно сохранить смысл обеих полезных правок.
- `git fetch` загружает refs и объекты без объединения с текущей веткой. `git pull` сначала делает fetch, затем merge или rebase в зависимости от настроек.
- `git push` отправляет локальные refs и необходимые объекты в remote.
- Тег — именованная ссылка на определённую версию; аннотированный тег содержит метаданные. Коммит — снимок изменения истории. Тег обычно остаётся на выбранном коммите.
- `.gitignore` исключает подходящие неотслеживаемые файлы из обычного добавления; уже отслеживаемый секрет он не удаляет из истории.
- Пароли и `.env` не публикуют: секреты могут остаться в истории, форках и копиях. При утечке нужен отзыв/ротация секрета.
- Если локальный код отличается: `git status`, сохранить работу коммитом или stash, `git fetch`, изучить `git log --graph --all` и `git diff main origin/main`, затем согласованно merge/rebase и решить конфликты. Не использовать force push без понимания последствий.

## Docker и PostgreSQL

- Docker упаковывает приложение и его окружение в образ, запускает изолированные контейнеры и упрощает воспроизводимый запуск.
- Образ — шаблон слоёв и конфигурации; контейнер — запущенный или остановленный экземпляр образа со своим writable layer.
- `FROM` задаёт базовый образ или начало нового этапа.
- `WORKDIR` задаёт каталог для следующих инструкций и команды запуска.
- `RUN` выполняется при сборке образа; `CMD` задаёт команду/аргументы по умолчанию при запуске. ENTRYPOINT определяет основную исполняемую команду.
- `COPY` копирует локальные файлы из build context или другого этапа. `ADD` имеет дополнительные функции, например распаковку локальных tar-архивов; для обычного копирования удобнее COPY.
- `EXPOSE 8080` документирует порт контейнера, но не публикует его на хост.
- `docker build -t name:tag .` собирает образ из Dockerfile и контекста.
- Multi-stage build собирает JAR в JDK-этапе, затем копирует его в JRE-этап. В итоговый образ не попадают Gradle, исходники и инструменты компиляции.
- Запуск с портом: `docker run --rm -p 8080:8080 name:tag`. Для локального доступа безопаснее `-p 127.0.0.1:8080:8080`.
- `docker stop` останавливает контейнер; `docker rm` удаляет контейнер. Сам образ при этом остаётся.
- Логи: `docker logs CONTAINER` или `docker compose logs app`.
- Команда внутри: `docker exec CONTAINER java -version` или `docker compose exec app java -version`.
- Docker Compose описывает несколько сервисов, их переменные, зависимости, сети и volumes в YAML. Здесь запускает API и PostgreSQL вместе.
- Сеть соединяет контейнеры и даёт DNS-имена сервисов; volume сохраняет файлы независимо от жизненного цикла контейнера.
- PostgreSQL volume сохраняет записи после удаления и повторного создания контейнера. `docker compose down -v` удаляет volume с данными.
- В контейнере API localhost относится к самому API; база находится в другом контейнере и доступна по имени сервиса `db`.
- Healthcheck PostgreSQL выполняет `pg_isready`; `depends_on: condition: service_healthy` задерживает старт API до готовности БД. Это не гарантирует исправность всех запросов приложения.
- DB credentials передаются через переменные окружения из локального `.env` или через secrets/внешнее хранилище. Их не зашивают в образ и Git.
- Если API не подключается к базе: `docker compose ps`, логи app/db, healthcheck, DB_URL с db:5432, имя БД и пользователя, совпадение пароля, общая сеть. У существующего volume POSTGRES_PASSWORD не меняет ранее созданный пароль автоматически.

## Jenkins и CI

- Jenkins — сервер автоматизации. Job — настроенная задача; build — отдельный её запуск.
- Jenkinsfile — файл с pipeline в репозитории: стадии, команды, агент, условия и обработка результата.
- Declarative Pipeline использует структурированный `pipeline { stages {...} }`; Scripted Pipeline — более свободный Groovy-код, обычно внутри node.
- Controller хранит конфигурацию и планирует работу; agent исполняет сборки. Для учебного окружения используется отдельный доверенный Docker-capable агент.
- Checkout получает нужную версию исходников из SCM.
- Build компилирует код и создаёт артефакт. Test выполняет автоматические проверки и сохраняет результаты JUnit.
- Автотесты до выпуска выявляют регрессии и не дают распространять заведомо неисправную версию.
- При ненулевом коде `sh` или провале Gradle test стадия падает; следующие обычные stages пропускаются. Блоки post выполняются согласно своим условиям. Не следует скрывать сбой через `|| true`.
- Docker Build требует Docker CLI и доступный daemon/build engine. Наличие Java само по себе этого не обеспечивает.
- Verify проверяет существование образа и выводит ID, размер и время создания.
- Jenkins Credentials хранят секреты централизованно; pipeline использует credentialsId и ограниченный scope вместо литералов в коде.
- Для private GitHub repo Jenkins использует Credentials с ограниченным токеном или SSH-ключом, назначенные SCM-конфигурации.
- Trigger запускает сборку по событию. GitHub webhook посылает уведомление Jenkins; polling периодически проверяет изменения в remote.
- CI — регулярная интеграция, сборка и проверка изменений. Continuous Delivery — готовность к выпуску с ручным решением. Continuous Deployment — автоматический выпуск успешно проверенных изменений.
- Console Output содержит источник запуска, checkout/commit, этапы, stdout/stderr, ошибки и итог; секреты туда выводить нельзя.
- Если Gradle упал: найти первую ошибку в Console Output, проверить JDK/Wrapper/зависимости, открыть результаты тестов, воспроизвести `./gradlew test --stacktrace`, исправить отдельным коммитом и перезапустить.
- Если сборка Java прошла, но Docker Build упал: проверить Docker CLI/daemon/права агента, Dockerfile, build context, путь JAR, доступ к registry, место на диске и архитектуру. Успешная компиляция не доказывает исправность Docker-конфигурации.

## Как показать проект преподавателю

1. Открыть README и GET /, назвать автора, группу, ID и личный URL.
2. Показать Linux-скрипт, terminal evidence, права 744, лог, grep и backup.
3. Показать Git graph, две feature-ветки, CRUD-доработку, merge conflict и его resolution commit, remote и тег.
4. Показать Dockerfile, Compose, `docker compose ps`, логи и параметры сети/volume.
5. Показать CRUD и ошибки API из evidence/api-responses.json.
6. Создать запись, перезапустить Compose без удаления volume, повторно получить ID.
7. Показать Jenkins stages, успешный запуск, намеренный failed test на личной ветке, исправление и новый success.
8. Показать автоматический запуск после push и объяснить CI/CD.
